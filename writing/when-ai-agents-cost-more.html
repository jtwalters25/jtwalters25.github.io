When AI Agents Cost More Than the Work They Automate

Orchestration, engineering skills, and knowing when to simplify.

By Jeremiah Walters · November 2026

I recently spent some time experimenting with making an existing engineering workflow more agentic.

The goal was straightforward: take a process that already worked, introduce AI agents to handle some of the coordination and repetitive work, and see whether we could improve efficiency without sacrificing correctness.

The process involved turning engineering requirements into code patterns, examples, detection rules, and validation results. We already had tools and reusable skills for most of that work. What I wanted to explore was whether agents could connect those capabilities more effectively.

The first experiment was promising. A worker gathered evidence. An evaluator reviewed the conclusions. The workflow produced a useful, human-accepted research result.

Then I tried to measure whether that approach was actually better than using the existing skills directly. That's where things got interesting.

Across two attempts, the orchestration consumed more than four million input tokens before either comparison task started. No comparison results. No baseline. No measurable improvement.

The agents weren't struggling with the engineering problem. They hadn't reached it yet.

That experience changed how I think about agentic engineering. Here are the lessons I'm taking forward.

1. The Coordinator Can Become More Expensive Than the Work

My initial design followed a familiar multi-agent pattern. One agent would perform research. Another would evaluate the results. A coordinating process would manage assignments, preserve state, handle feedback, and determine when the work was ready for human review.

On paper, it made sense. Responsibilities were separated. Evidence was preserved. Each stage had clear expectations.

And the first research pilot worked. It used an existing engineering skill, a Worker, and an Evaluator to investigate a reliability requirement. The result was grounded in source evidence, acknowledged uncertainty, and was accepted after human review. The pilot consumed approximately 475,000 input tokens.

Then I decided to compare that approach against the existing skill-led workflow. The comparison was supposed to be simple:

  • Arm A: Use the existing engineering skills directly.
  • Arm B: Use those same skills with Worker/Evaluator coordination.

Both would receive identical evidence, permissions, and evaluation criteria.

But before either arm could run, the coordinator needed to establish the experimental conditions. That meant verifying source versions, budgets, permissions, review processes, execution order, and handoff requirements.

Each decision introduced more context. Each subsequent interaction carried more of that context forward. Eventually, preparation exhausted the resource allowance before either arm launched.

I tried again with a smaller execution context. The second attempt also exhausted its budget before the research began.

The numbers

ActivityInput tokensOutcome
Initial research pilot~475,000Completed and accepted
A/B coordination attempts~4.25 millionNeither arm launched

These figures came from recorded usage receipts. They are not billing totals, and the coordination subtotal excludes some additional activity.

Without detailed per-call attribution, I can't definitively say which coordination activities consumed the most tokens. But the overall result was clear: we spent substantially more effort preparing to compare the work than performing the original research task.

What I'd do differently

I'd avoid using a long-running conversational agent to coordinate independent engineering tasks unless that coordination provides a measurable benefit. Instead:

  • Record the task and inputs once.
  • Keep execution contexts small.
  • Run independent tasks independently.
  • Pass artifacts instead of entire conversation histories.
  • Measure coordination overhead separately from execution.

A coordinator should exist because coordination adds value, not simply because the architecture supports another agent.

Lesson: Every agent handoff has a cost. Make sure the coordination is worth it.

2. Before Building Another Agent, Look at What You Already Have

One of the most useful exercises wasn't building an agent. It was taking inventory of the capabilities we already had.

Our engineering repository contained 26 reusable skill definitions covering activities such as:

  • Requirements analysis
  • Pattern discovery
  • Code sample development
  • Rule authoring
  • Tool selection
  • Validation
  • Code review
  • Historical incident investigation

Initially, I considered introducing specialized agents around several of these responsibilities. But the inventory exposed an important distinction: a capability doesn't need to become an agent just because an agent could perform it.

If an existing skill already knows how to generate a detection rule, why create another agent responsible for rule generation? If a deterministic test runner already validates the result, why ask an LLM to simulate that validation? If an established tool already retrieves source evidence, why duplicate the retrieval process?

The more useful question became: what part of this workflow actually requires additional reasoning or coordination?

Sometimes the answer was independent evidence review. Sometimes it was selecting the appropriate existing tool. And sometimes the existing process was already sufficient.

The simpler approach

Instead of building a large collection of specialized agents, I settled on a more selective model:

Existing skill → Optional independent evaluation → Human decision

For straightforward work, use the existing skill. For complex or ambiguous work, introduce an evaluator when independent review could meaningfully improve the result. For implementation and validation, continue using established engineering tools.

It's not necessarily the most exciting architecture diagram. But it's easier to reason about, easier to maintain, and much less expensive to coordinate.

Lesson: Reuse capabilities before introducing agents. More agents don't automatically mean more value.

3. Sometimes the Best Agent Decision Is Not to Act

One of the more encouraging results came from an investigation that didn't produce a code change.

The task involved determining whether an outbound dependency path had an effective concurrency limit. The agent examined source evidence, configuration, supporting code, and counterexamples. The evaluator then reviewed the conclusions.

The investigation found an existing concurrency-control mechanism. However, the available evidence couldn't establish its effective process-wide behavior under actual deployment conditions. Several important details remained unresolved.

The workflow could have overreached. It could have interpreted incomplete evidence as a violation, recommended another detection rule, or suggested a configuration change.

Instead, it produced a qualified finding and stopped. No confirmed production violation. No established detector defect. No justified code change.

That was the correct outcome.

Why this matters

We often measure AI agents by whether they complete tasks. But in engineering, knowing when not to proceed is part of completing a task correctly.

An agent that confidently recommends changes from incomplete evidence can create more work than it eliminates. An agent that identifies uncertainty, explains what's missing, and stops at the right boundary can be genuinely useful.

I started thinking about abstention differently. It's not necessarily a failure state. Sometimes it's the most responsible output.

Lesson: A trustworthy agent should be able to say, "The evidence doesn't justify a change."

4. Passing Tests Doesn't Mean You've Demonstrated Value

After simplifying the approach, I returned to a more practical experiment. Instead of comparing elaborate agent architectures, I opened a clean development workspace and gave Copilot one engineering task: find a narrow detection gap, improve the existing rule, add regression fixtures, and validate the result.

No parent coordinator. No A/B experiment. No additional agents. Just the existing engineering skills and tools.

The task involved improving a static-analysis rule that recognized a particular problematic coding pattern but missed a related syntax variation. The improvement was small and well scoped. We extended the matcher, added positive and negative fixtures, and ran the validation suite.

The tests passed. Then a review identified a potential false positive: the new matcher could recognize a similar operation on an unrelated data structure. That was a legitimate issue.

We tightened the rule, added regression cases, and validated it again. 360 tests passed. The build passed. The other local validation checks passed. At that point, the implementation looked healthy.

But local correctness was only part of the question. We still needed to know whether the improvement was useful against representative source code. So we evaluated the previous and updated rule versions against selected real repositories.

Both versions produced zero findings.

Was that a failure? Not necessarily. The local fixtures demonstrated that the matcher recognized the intended syntax and rejected the tested counterexamples. The representative scan didn't reveal false positives. But it also didn't contain a production example exercising the new detection branch. That meant we couldn't establish real-world precision or improved recall for the new behavior.

The tests proved the implementation behaved as expected under the tested conditions. They didn't prove the change delivered additional production coverage.

Interestingly, the repository investigation revealed a different limitation. A relevant value was constructed in one location and later passed through an intermediate collection before reaching its final destination. The syntax-local rule couldn't establish that relationship.

That was potentially a more meaningful detection opportunity, but it also required a different kind of analysis. The right response wasn't to keep expanding the existing matcher until it recognized everything. It was to investigate whether a relationship-aware analysis tool would be more appropriate.

What this taught me

Agent-generated code needs the same engineering discipline as human-generated code. A green test suite is important. But we should distinguish:

  • Execution correctness: Did the workflow run?
  • Technical correctness: Does the output satisfy its specification?
  • Representative validity: Does it behave correctly under realistic conditions?
  • Outcome value: Did it actually improve something that matters?

Those are different levels of evidence.

Lesson: A successful execution isn't necessarily a successful engineering outcome.

5. The Experiment Was Becoming the Project

Looking back, this may have been my biggest mistake.

I started with a straightforward engineering objective. I wanted to make an existing process more efficient. But over time, I found myself spending more effort on the experimental machinery than on the engineering work. I was designing:

  • Agent responsibilities
  • Handoff contracts
  • State management
  • Approval checkpoints
  • Evaluation protocols
  • Resource budgets
  • Execution manifests
  • Comparison procedures

Each addition seemed reasonable. Each solved a problem introduced by the previous layer. Eventually, the experiment had become a system of its own, and that system was expensive to operate.

The turning point came when I stopped trying to perfect the comparison and returned to the original engineering task. I opened a clean workspace. I used the existing skills. I asked for one defensible improvement.

The result wasn't revolutionary. But it was tangible. We identified a coverage gap, improved a rule, caught a false-positive risk, added tests, and evaluated the candidate against representative code. We also learned where the rule's limitations were.

That was real engineering progress. And it didn't require a sophisticated orchestration framework.

The lesson I wish I'd started with

Prove the smallest useful workflow before designing the system that coordinates it.

It's easy to justify complexity incrementally. It's harder to step back and ask whether the complexity is improving the outcome. Sometimes the most important architectural decision is deciding what not to build.

Lesson: If the experiment requires more engineering than the problem you're trying to solve, it's time to simplify.

6. What I'd Do Differently Next Time

I haven't abandoned agentic engineering. But I'd approach the next experiment differently.

Start with one real task

Before designing a multi-agent system, demonstrate that one agent using existing tools can produce a useful result.

Inventory existing capabilities

Don't introduce agents to recreate functionality already provided by skills, scripts, APIs, or engineering pipelines.

Keep context small

Avoid carrying entire experiment histories through long-running coordination conversations. Use concise task inputs and artifact-based handoffs.

Measure the entire workflow

Include preparation, coordination, execution, validation, human review, and rework. Optimizing only the agent's execution time can hide the actual cost.

Make evidence part of the output

Require sources, assumptions, counterexamples, and explicit uncertainty. Don't accept plausible conclusions as verified conclusions.

Validate beyond synthetic examples

Use realistic inputs and representative environments. A test suite can demonstrate technical behavior without establishing real-world usefulness.

Introduce evaluators selectively

Independent review can be valuable, especially when evidence is ambiguous or the consequences of a wrong conclusion are significant. But it doesn't need to be mandatory for every task.

Know when to stop

If coordination becomes more expensive than execution, reconsider whether the orchestration is necessary. And if the evidence doesn't justify a change, don't force one.

So, Did the Experiment Work?

That's a more complicated question than I expected.

Some parts worked. The research workflow produced an evidence-backed result and appropriately stopped when the evidence was insufficient. The simpler skill-led process produced a locally validated detection improvement. The existing tools and skills proved capable of handling much of the engineering work without additional orchestration.

Other parts didn't. The formal multi-agent comparison never executed because coordination exhausted its resource budget. The detection improvement passed local tests but didn't demonstrate additional real-world coverage in the representative sample. And we never established whether Worker/Evaluator coordination improved productivity compared with the existing skill-led process.

I wouldn't call the overall effort a completed success. But I wouldn't call it wasted effort either. The experiments helped distinguish what was technically possible from what was operationally useful.

They also changed the questions I ask when designing agentic systems. I'm less interested in how many agents I can coordinate. I'm more interested in:

  • How much human effort does this actually remove?
  • How much coordination overhead does it introduce?
  • Can I verify the output?
  • What happens when the evidence is incomplete?
  • Does the additional complexity improve the result?
  • Can I demonstrate improvement against the existing process?

Those questions feel more important than the number of agents in the architecture.

Final Thoughts

I started these experiments wanting to make engineering workflows more agentic. What I learned is that adding agents is often the easy part. The harder work is making the system efficient, trustworthy, measurable, and useful.

More autonomy doesn't automatically create more value. More sophisticated orchestration doesn't automatically produce better outcomes. And passing every test doesn't necessarily mean you've solved a meaningful problem.

Sometimes the best improvement is another agent. Sometimes it's a better tool. Sometimes it's an existing skill. And sometimes it's removing the coordination layer entirely.

The goal of agentic engineering shouldn't be to maximize autonomy. It should be to minimize the total effort required to reach a correct, evidence-backed outcome.

That's the principle I'll be carrying into my next experiment.

I'm curious how others are approaching this. If you've been experimenting with agentic engineering, where have you seen the biggest unexpected costs: orchestration, context management, evaluation, or something else?
