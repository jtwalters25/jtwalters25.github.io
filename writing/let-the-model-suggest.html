Let the Model Suggest, Let Code Decide

How to use a language model to understand a request without letting it decide the outcome. Explained with a babysitter, then built in code.

By Jeremiah Walters · November 2026

Netflix recently published how they engineered AI Discover. One line in it is the whole idea of this post: "An LLM can propose the path, but code decides whether it runs." [1]

That sentence is easy to agree with and surprisingly hard to build. I've been building it since February in a side project called Intent Engine, which re-ranks what kids see on TV based on the moment, not just the age rating. This post explains one thing: how you keep a model useful without ever giving it the final say. We'll start with a babysitter and end with the code.

Start With a Babysitter

You're heading out for the night. Before you leave, you tell the babysitter the house rules: nothing rated above the kids' level, screens off at 8:30.

The babysitter is genuinely helpful. They read the room in a way your rules never could. "They're wired from dinner, let's put on something calm." That's a good suggestion, and you want it.

But there are things the babysitter doesn't get to decide. They can't decide tonight is special and the rules don't apply. And if they're unsure what to do, you'd rather they do the boring, safe thing than improvise.

Everything else in this post is how to make those three layers real, so they hold even when the model is wrong, slow, or being manipulated.

Step 1: Decide What the Model Is Allowed to Say

The babysitter's job is to describe the moment, not to pick the show. In code, that means the model produces an intent, never a selection.

That boundary is a typed contract. Every object that might come from a probabilistic component inherits a base that rejects unknown fields instead of quietly ignoring them. Snippets here are trimmed; the full files are in the repo.

class AgenticContract(BaseModel):
    """Strict base configuration for data that may originate from an agent."""
    model_config = ConfigDict(extra="forbid", ...)

class IntentStep(AgenticContract):
    """One time-relative intent state; never a candidate selection."""
    step_id: str
    offset_minutes: int = Field(..., ge=0, strict=True)
    intent: Dict[str, Any]
    transition_reason: str

A plan is a short sequence of these steps, at most five with strictly increasing time offsets, so it can say "calm now, quiet by 8:15" without naming a show. If a step tries to sneak a selection in anyway, the validator catches the words that mean "I picked something":

FORBIDDEN_SELECTION_SIGNALS = frozenset({
    "candidate_id", "final_score", "item_id", "rank",
    "ranked_items", "recommended_item", "recommended_title",
    "score", "selected_candidate", "selected_candidate_id",
})

if selection_sensitive and name.lower() in FORBIDDEN_SELECTION_SIGNALS:
    issues.append(ValidationIssue(
        code="candidate_selection_forbidden",
        message="intent steps cannot select or score candidates"))

Every other signal must be one the domain supports, with a value in range. For streaming, that's energy between 0 and 1, viewer, tone, runtime_preference, time_bucket, and an intent_type from a fixed set. Anything else fails as unknown_signal or invalid_signal_value.

Lesson: Decide what the model is allowed to say before you decide what it says. A narrow output type is the cheapest guardrail you'll ever write.

Step 2: Only Ask When You Need To

A good babysitter checks the fridge note before calling you. Same here. Plain rules try first, and the model only gets asked when rules can't identify a single objective. The whole model path is off unless a server flag turns it on.

try:
    return super().interpret(goal)          # rules first
except InterpretationError as exc:
    if exc.code not in {"unsupported_goal", "ambiguous_goal"}:
        raise                                # bad input never reaches a model

When the model does answer, its output gets treated like a note from a stranger. It counts only if it clears every check:

  • Size. Responses over 32 KB are rejected.
  • Strict JSON. Duplicate keys and non-finite numbers like NaN fail parsing.
  • A known objective. One of wind_down, focus, family_time, quick_session or high_energy.
  • Enough confidence. Below 0.7, it's discarded.
  • Only allowed context. The model may describe energy, viewer and a time horizon. Nothing else.
  • No authority. The model can't create hard rules or claim to speak for the system.
if any(c.hard or c.source not in {ConstraintSource.USER,
                                  ConstraintSource.INFERRED}
       for c in interpretation.explicit_constraints):
    raise ValueError("model cannot claim authority")

That last check is the babysitter rule in code. The model can say a request sounds like a wind-down. It can't decide a maturity rule no longer applies.

Step 3: Check Before You Combine

This is the step I'd most want another engineer to steal, because it's easy to get backwards.

After the model answers, its interpretation gets combined with trusted values: what the parent set, what the request explicitly said. The tempting order is to combine first and validate once. The problem is that a trusted value can overwrite a bad model field, the combined result looks fine, and you never learn the model was wrong.

So the code checks the model's interpretation on its own first, then combines, then checks again:

# Validate semantics BEFORE trusted profile overrides or explicit
# user context could mask an invalid model field.
RuleBasedIntentPlanner().create_plan(interpretation, goal.domain, goal.timestamp)
merged = {**interpretation.inferred_context, **interpretation.entities, **context}
...
RuleBasedIntentPlanner().create_plan(checked, goal.domain, goal.timestamp)

Checking twice costs almost nothing. Checking once, after the merge, hides exactly the failures you most need to see.

Step 4: When in Doubt, Do the Boring Thing

If the babysitter isn't sure, you want the safe default, not creativity. In code, any failure in the model path drops to a neutral interpretation. No guessing, no retrying its way to an answer.

except Exception:
    # Do not log raw goals, model content, credentials or exception text.
    return ContextInterpretation(
        objective="safe_fallback", entities=context, confidence=0.0,
        assumptions=["Optional model interpretation was unavailable or invalid; "
                     "using explicit context and neutral intent only."])

Two details matter here. The fallback carries the house rules forward, so failing never means failing open. And it doesn't log the raw model output or the user's words, because failure paths are a common place for private data to leak.

The fallback plan also goes back through the validator, and its ID is a hash of its canonical JSON. Same inputs, same plan, same ID, which makes it easy to prove two runs did the same thing.

Step 5: Make the House Rules Unbreakable

Now the top layer. The validator separates constraints anyone can suggest from authoritative constraints: hard rules from a trusted source, like a parent's settings or the system's safety policy. Authoritative constraints must be hard and can't be inferred. And no plan may weaken one:

if not preserved:
    issues.append(ValidationIssue(
        code="hard_constraint_weakened",
        message=f"authoritative hard constraint {checked_authoritative.type!r} "
                "must be preserved exactly"))

The trusted profile also wins on identity. If a request or a model claims the viewer is an adult but the active profile says kids, the profile wins, and the plan records that policy overrode the input.

To be precise about where this stands: the public pilot runs with one server-owned kids profile and a hard viewer_maturity = kids rule. A real parent settings flow that feeds these constraints is the next piece. The authority model is built; the parent-facing side isn't.

Step 6: Leave a Note, and Try to Break It

A good babysitter leaves a note: what happened, and why. When a plan fails, the engine returns machine-readable issues with a code, a path and a message, like expired_plan, conflicting_constraint or hard_constraint_weakened. Each validation stage records a typed receipt, and that receipt's own schema refuses to be inconsistent: a passed stage can't carry issues, and a failed one must carry at least one. That's what lets you answer "why did my kid see this?" with evidence.

And a guardrail you haven't tried to break is a hope, not a guardrail. Each promise above has a test that attacks it. This one tries to quietly soften the maturity rule:

def test_authoritative_hard_constraint_cannot_be_weakened(self, validator):
    authoritative = _constraint(source=ConstraintSource.SYSTEM, hard=True)
    weakened = _constraint(source=ConstraintSource.SYSTEM, hard=False)
    plan = _plan(constraints=[weakened])

    with pytest.raises(PlanValidationError):
        validator.validate(plan, now=NOW,
                           authoritative_constraints=[authoritative])

A few others, by name, because together the names read like a threat model:

  • test_injection_in_goal_cannot_weaken_rules_policy: prompt injection in the user's words can't loosen the rules.
  • test_http_failures_reach_safe_fallback: timeouts, network errors, 429s and 503s all land on safe_fallback.
  • test_provider_failure_safe_and_no_content_logged: failures don't leak the request into logs.
  • test_provider_cannot_mutate_original_goal: the model gets a copy, so it can't rewrite the evidence.
  • test_redirect_handler_does_not_forward_credentials: a redirect from the model gateway can't carry the API key somewhere else.
  • test_fallback_is_deterministic_and_round_trips: two failures produce identical plans.

The backend suite is 1,239 tests, and the ones I trust most are the ones written to break things.

The Tradeoffs

None of this is free, and some of it is still weak.

Model confidence is self-reported. The 0.7 floor filters out answers the model itself is unsure of. It does nothing about a model that's confidently wrong. The real fix is calibrating against labeled examples: how often is a 0.8 actually right? I haven't done that yet.

Rules first caps the experience. If neither the rules nor the model can place a request, the answer is a neutral plan. Safe, and bland. For a kid at bedtime I'll take boring over wrong, but the rules have to keep getting better.

Failing closed can hide outages. If the model goes down, users quietly get the fallback and nobody complains, which is the point and also the danger. The receipts make fallbacks countable. Watching that rate is the next thing to wire up.

Strict schemas break on change. extra="forbid" means a model that starts adding a field gets rejected until the contract is updated. That's on purpose. I'd rather find out from a failed validation than from a field nobody checked.

The Same Instinct at Netflix Scale

Reading Netflix's post was mostly reassuring, because their system makes the same calls at a scale I'll never touch. [1]

  • They plan, then execute. Here, PlanValidator runs before any ranking.
  • The planner writes placeholders, and code fills in values like the maturity rating. Here, the trusted profile overrides whatever the model said about the viewer.
  • A slow or failed plan falls back to a tested one. Here, safe_fallback, validated like any other plan.
  • Every request leaves a structured record. Here, issue codes and typed receipts.

Varun Khaitan, one of the authors, put it best when he shared the post: "LLMs bring the imagination. Engineering brings the guarantees." [2]

The one real difference is who's steering. In Discover, the person steering is the person watching. In Intent Engine, the person steering is usually out for the night. The parent sets intent once, and it governs every request after, including the ones they never see. That's why the babysitter, and not the viewer, is the right mental model for this system.

What I Don't Know Yet

Plenty. Zero customers. Netflix asks a question in their post I can't answer yet either: do people want to steer, or lean back? For parents, that's everything. If setting the house rules feels like a chore, they won't get set. That's what I'm testing next, with real families.

The demo is the easy part. Trustworthy at scale is the work. If you want to poke at the approach, the live demo and the code are both open.
